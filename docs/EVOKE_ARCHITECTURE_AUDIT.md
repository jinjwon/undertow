# Evoke 아키텍처 감사 및 발전 계획

- 기준: `feat/chat-rich` 브랜치, `desktop/package.json` 버전 2.4.0, 2026-11-11
- 범위: 분석과 계획만. 이 문서를 쓰면서 애플리케이션 코드는 바꾸지 않았다.
- 표기: **[확인]** 은 이 저장소의 코드나 테스트 실행으로 직접 본 것, **[문서]** 는 외부 프로젝트의 공식 문서나 저장소에서 읽은 것, **[미검증]** 은 아직 돌려 보지 않은 가정이다. [미검증] 항목은 Phase 0 스파이크에서 확인한다.

## 결론 요약

1. **Code - OSS로 전환하지 않는다.** 현재 Electron 셸과 Evoke UI를 유지하고, 편집 엔진만 "맨 Monaco"에서 "VS Code 서비스가 붙은 Monaco"(`monaco-vscode-api`)로 바꾸는 하이브리드(Option C)를 추천한다. 단, 이 추천은 Phase 0 스파이크가 통과해야 확정된다.
2. 지금의 Evoke는 "VS Code급 IDE의 초기 버전"이 아니라 **에이전트 터미널 옆에 파일 보기와 편집기를 붙인 앱**이다. LSP, 디버깅, 확장, 태스크, 명령 팔레트, 파일 생성/이름 변경/삭제, Git 쓰기 동작은 코드가 한 줄도 없다.
3. 가장 값진 기존 자산은 UI가 아니라 **경계**다. 메인 프로세스의 파일 접근 가드, Claude Code IDE 링크(`ide.cjs`), 순수 함수로 된 레이아웃 기하(`layout.ts`), 3개 언어 문자열 테스트. 이것들은 어떤 대안을 골라도 살린다.
4. 엔진을 바꾸기 전에 먼저 할 일이 있다. 설정이 전부 렌더러의 `localStorage`에 있어서, 페이지를 불러오는 주소가 바뀌면 사용자 설정이 사라진다. 저장소를 메인 프로세스 파일로 옮기는 것이 첫 작업이다.

### 1.2 프로세스와 통신 [확인]

```
┌─ Main (main.cjs) ──────────────────────────────────────────────┐
│ roots/picked (열린 폴더 집합) ── guard(realpath) ── fs:*        │
│ git (execFile)   node-pty (terms Map)   claude -p (chats Map)  │
│ serve.cjs (127.0.0.1 미리보기)   ide.cjs (127.0.0.1 WS, MCP)   │
└────────────── ipcMain.handle / webContents.send ───────────────┘
                         │ preload.cjs (contextBridge, 35개 메서드)
┌─ Renderer (sandbox, contextIsolation) ─────────────────────────┐
│ App.tsx: useState 약 45개, 전역 keydown 1개                     │
│ Monaco(@monaco-editor/react)  xterm.js  iframe(미리보기)        │
└────────────────────────────────────────────────────────────────┘
        ▲ WebSocket(MCP)                     ▲ PTY
   Claude Code CLI (터미널 안)          Codex CLI / 셸 / ssh
```

- 창은 하나다 (`main.cjs:354`). `sandbox: true`, `contextIsolation: true`, 새 창과 탐색 금지, 권한 요청 전부 거부 (`main.cjs:362-367`).
- 페이지는 `file://`로 불러온다 (`main.cjs:369`, `vite.config.mjs`의 `base: './'`). CSP는 `default-src 'self'`이고 `unsafe-eval`이 없다 (`index.html`).
- 파일 접근은 전부 `guard`를 지난다. `guard`는 실제 경로(realpath)가 열린 프로젝트 안인지 본다 (`main.cjs:21-26`). 프로젝트는 Claude Code나 Codex가 신뢰한 폴더, 또는 대화상자에서 고른 폴더만 열린다 (`main.cjs:44-51`).
- 패키징된 앱은 Electron fuse로 `runAsNode` 등을 끈다 (`package.json`의 `electronFuses`).

### 1.3 상태 관리 [확인]

- 상태 라이브러리가 없다. `App` 컴포넌트 하나가 `useState` 약 45개를 갖는다 (`App.tsx:97-161`).
- 최신 값을 이벤트 핸들러에 넘기려고 `live` ref를 쓴다 (`App.tsx:527-528`).
- 영속 저장은 전부 `localStorage`다: `theme`, `lang`, `layout`, `split`, `terminal`, `agents`, `motion`, `layoutPresets`. 프로젝트별 상태(열린 탭, 선택한 메뉴)는 저장하지 않는다.
- `window.evoke`의 타입은 `any`다 (`App.tsx:18`). 프로젝트에 `tsc`가 없어서 타입은 에디터에서만 검사된다.

### 2.3 빌드, 테스트, 배포 [확인]

- 테스트: `node --test`로 8개 파일. 이 문서를 쓰면서 실행한 결과 **61개 통과, 0개 실패**. 전부 순수 함수 테스트다. 컴포넌트, IPC, 실제 창을 띄우는 테스트는 없다.
- CI: PR마다 Ubuntu에서 test, audit(high 이상 실패), build. macOS와 Windows에서는 돌지 않는다.
- 배포: 태그를 밀면 macOS는 dmg(arm64), Windows는 NSIS(x64)를 만든다. macOS 서명은 ad-hoc(`sign-mac.sh`)이라 공증이 없고, 첫 실행에 "열기"가 필요하다.
- **자동 업데이트가 없다.** `electron-updater`도 `autoUpdater`도 쓰지 않는다.
- 플러그인은 GitHub에서 설치된 사본이 돌기 때문에, 저장소 수정은 병합과 플러그인 업데이트 뒤에야 반영된다.

## 3. 유지 / 개선 / 교체 대상

| # | 영역 | 분류 | 판단 근거 |
|---|---|---|---|
| 1 | 디렉터리 구조 | 개선 | `desktop/src/`가 평평하다. 엔진과 UI를 나누는 폴더 경계가 필요하다. |
| 2 | Electron Main | 개선 | 가드와 보안 설정은 유지. `main.cjs` 하나에 모든 서비스가 있으므로 서비스별 모듈로 나눈다. |
| 3 | Preload / IPC | 개선 | 통로가 하나뿐인 구조는 유지. 타입이 없고 채널이 문자열로 흩어져 있으니 채널 표 하나와 타입을 둔다. |
| 4 | 프론트엔드 / 상태 | 개선 | React, Vite 유지. `App.tsx`의 상태를 영역별 스토어로 나눈다. |

| 6 | 파일 시스템 | 개선 | 가드 유지. 생성/이름 변경/삭제, 파일 감시, 트리 갱신을 더한다. |
| 7 | Git | 개선 | `execFile` 방식 유지. 쓰기 동작을 더하거나, 확장 호스트가 붙으면 VS Code 내장 Git 확장에 맡긴다. |
| 7 | 터미널 | 개선 | node-pty와 xterm 유지. 세션 id를 `종류:경로`에서 고유 id로 바꿔야 병렬이 된다. |
| 8 | Claude Code 연동 | 유지 | IDE 링크와 stream-json 채팅은 그대로 둔다. 엔진을 바꿔도 `ideTools`의 계약은 같다. |
| 8 | Codex 연동 | 개선 | PTY 실행은 유지. 구조화된 상태를 얻을 방법을 조사해야 한다 [미검증]. |
| 9 | UI 편집 모드 | 개선 | 이동, 크기 조절, 스냅, 교환, 프리셋, 미리보기는 그대로 쓴다. 패널이 3개로 고정된 것만 푼다. |
| 10 | 레이아웃 저장 | 개선 | 분수 좌표와 `parseLayout`의 방어적 파싱은 유지. 저장 위치를 `localStorage`에서 파일로 옮긴다. |
| 11 | 테마 / 토큰 | 개선 | CSS 변수 구조 유지. 테마 하나가 세 곳(`style.css`, `themes.ts`, `tokens.js`)에 흩어진 것을 한 정의로 모은다. |
| 12 | 플러그인 | 유지 | Claude Code 플러그인은 별개 제품으로 유지한다. VS Code 확장과 이름이 섞이지 않게 문서에서 "플러그인(Claude Code)"과 "확장(VS Code)"으로 구분한다. |
| 13 | 빌드 / 배포 | 개선 | electron-builder 유지. 자동 업데이트와 공증을 더한다. |
| 14 | 테스트 / CI | 개선 | 순수 함수 테스트 방식 유지. 창을 띄우는 스모크 테스트와 macOS/Windows 러너를 더한다. |

교체는 한 곳(편집 엔진)뿐이다.

## 4. VS Code 호환성 분석

"VS Code 확장이 돈다"는 말은 네 가지를 뜻한다. 서로 다른 문제다.

| 층 | 무엇인가 | Monaco만으로 되는가 |
|---|---|---|
| ① 편집기 위젯 | 텍스트 모델, 커서, 렌더링, diff | 된다. Monaco가 이것이다. |
| ② 워크벤치 서비스 | 파일 서비스, 설정, 키바인딩, 명령, 언어 기능 레지스트리, TextMate, 테마, 검색, SCM, 디버그 서비스, 터미널 서비스 | **안 된다.** Monaco에는 이 서비스들의 빈 대체물만 있다. |
| ③ Extension Host | 확장을 불러와 `vscode` API를 주는 별도 프로세스(Node) 또는 워커(Web). 렌더러와 RPC로 말한다. | **안 된다.** Monaco에 없다. |
| ④ 확장 UI 자리 | 트리 뷰, 웹뷰, 상태 표시줄 항목, 커스텀 에디터, 빠른 선택, 알림. 확장이 "여기에 그려 달라"고 요청하는 곳. | **안 된다.** 워크벤치 UI의 일부다. |

여기에 프로토콜 두 개가 더 있다.

- **LSP**: 언어 서버와 말하는 프로토콜. 언어 서버는 보통 확장이 실행한다(확장이 `vscode-languageclient`로 서버를 띄운다). 확장 없이 서버만 직접 띄울 수도 있지만, 그러면 서버마다 설치와 설정을 Evoke가 책임져야 한다.
- **DAP**: 디버그 어댑터와 말하는 프로토콜. 어댑터도 확장이 제공한다. 어댑터만으로는 부족하고, 중단점/호출 스택/변수 UI가 필요하다.

### 4.1 확장 종류별 요구 사항

| 확장 종류 | 예 | 필요한 층 |
|---|---|---|
| 선언형 (문법, 테마, 스니펫, 아이콘) | 색 테마, 언어 문법 | ② |
| 웹 확장 (브라우저에서 도는 것) | 일부 포매터, 마크다운 도구 | ② + ③(워커) |
| Node 확장 | ESLint, Prettier, rust-analyzer, Python, GitLens | ② + ③(Node) + 대개 ④ |
| 디버거 | Node 디버거, debugpy, CodeLLDB | ② + ③(Node) + DAP + 디버그 UI |
| 네이티브 의존 확장 | 플랫폼별 바이너리를 가진 것 | 위 + 플랫폼별 VSIX 선택 |

쓸 만한 확장은 대부분 Node 확장이다. 워커 확장만 지원해서는 "VS Code 확장 호환"이라고 말할 수 없다.

### 4.2 Marketplace와 Open VSX

- **VS Code Marketplace는 쓸 수 없다.** 이용 약관이 Marketplace의 확장을 Microsoft의 지정 제품(Visual Studio, VS Code, GitHub Codespaces, Azure DevOps 등)에서만 설치하고 쓰도록 제한한다. 약관 원문은 직접 읽지 못했고, 약관을 인용한 기사 3건에서 같은 내용을 확인했다 [문서, 2차 출처]. 출시 전에 원문(`aka.ms/vsmarketplace-ToU`)을 직접 확인해야 한다.
- **Open VSX**(Eclipse 재단)가 대안이다. VSCodium, Theia, Cursor, Windsurf 계열이 쓴다. 확장 게시자가 직접 올려야 하므로 Marketplace에 있는 확장이 전부 있지는 않다.
- **Microsoft의 일부 확장은 라이선스로 막혀 있다.** Pylance, C/C++(cpptools), C# Dev Kit, Remote 계열, Live Share는 라이선스가 Microsoft 제품에서만 쓰도록 한다. Open VSX에 없고, VSIX를 따로 구해 설치해도 라이선스 위반이다. **기술로 풀 수 없는 제약이다.**
- 대체재: Python은 Pyright 계열, C/C++은 clangd, C#은 오픈소스 언어 서버. 기능 차이가 있다.
- "VS Code" 이름과 로고는 Microsoft 상표다. 제품 설명에 "VS Code 확장 호환"이라고 쓸 수 있는지는 법률 검토 대상이다.
- VS Code의 `vscode.proposed.*` API를 쓰는 확장은 정식 VS Code에서도 허용 목록에 있어야 돈다. 대상에서 뺀다.

## 5. 세 가지 아키텍처 대안 비교

### Option A. 현재 Electron + 맨 Monaco 유지, 기능을 직접 구현

- **할 수 있는 것**: LSP 클라이언트를 직접 붙여 언어 서버 몇 개를 지원한다. DAP 클라이언트와 디버그 UI를 직접 만든다. Git, 검색, 태스크를 직접 만든다.
- **할 수 없는 것**: VS Code 확장 실행. `vscode` API는 네임스페이스 수십 개, 기여 지점 수십 개이고 매달 바뀐다. 이것을 다시 구현하는 것이 Theia가 여러 해 동안 여러 회사와 해 온 일이고, 지금도 일부는 빈 구현(stub)이다 [문서].
- 참고: 널리 쓰이는 `monaco-languageclient`도 지금은 `monaco-vscode-api` 위에서 도는 것으로 알고 있다 [미검증, 이번에 문서를 읽지 않음]. "맨 Monaco에 LSP만 붙인다"는 경로는 사실상 Option C로 들어가는 길이다.
- **판정**: "언어 지원 몇 개가 있는 가벼운 편집기"가 목표라면 맞다. 확장 호환이 핵심 정의인 이상 탈락.

### Option B. Code - OSS 포크로 전환 (또는 Theia)

- **얻는 것**: ②③④ 전부, 디버그, 태스크, SCM, 설정, 키바인딩, 멀티 루트. 호환성이 가장 높다. Cursor, Windsurf, VSCodium이 이 길이다.
- **Evoke 코드 재사용**: 낮다. 메인 프로세스의 가드, PTY, 미리보기는 VS Code가 자기 것을 갖고 있어서 대부분 버린다. React UI는 워크벤치 기여(TypeScript, 자체 DOM/위젯 체계)로 다시 써야 한다. 살아남는 것은 IDE 링크 로직(확장으로 옮김), 레이아웃 기하의 아이디어, 디자인 토큰, 문자열이다.
- **독자 UI 가능 범위**: 색, 글꼴, 아이콘은 테마로 된다. 탭 모양, 패널 구조, 내비게이션은 워크벤치의 `Part`/그리드 코드를 직접 고쳐야 한다. 고친 만큼 매달 업스트림 병합에서 충돌한다. 자유 배치(겹치는 위젯, 분수 좌표 사각형)는 워크벤치 그리드와 맞지 않는다.
- **UI 커스터마이징**: VS Code는 뷰를 사이드바/패널/보조 사이드바 사이로 옮기는 기능을 이미 갖고 있다. 그 범위 안이면 공짜지만, Evoke의 편집 모드(숫자 입력, 스냅 가이드, 프리셋)는 다시 만들어야 한다.
- **빌드/배포**: 저장소가 크고 전체 빌드가 길다. `product.json`, 아이콘, 업데이트 서버, 갤러리 주소를 직접 꾸려야 한다. Microsoft 공식 빌드에 들어가는 비공개 부분(원격 서버 바이너리, 일부 내장 확장)은 포크에 없다.
- **라이선스**: Code - OSS 소스는 MIT. Marketplace와 Microsoft 전용 확장 제약은 4.2와 같다. 포크라고 풀리지 않는다.
- **Theia 변형**: 커스텀 제품을 만들라고 설계된 프레임워크라 포크보다 병합 부담이 작다. 도킹 레이아웃(탭, 분할)을 기본으로 준다. 대신 확장 API 일부가 빈 구현이고 [문서], 자체 DI 프레임워크를 배워야 하며, UI는 역시 처음부터 다시 만든다.
- **판정**: 호환성은 최고, 비용도 최고. 1인 개발 규모에서 "Evoke만의 UI"를 유지하면서 매달 업스트림을 따라가는 것은 지속하기 어렵다. Option C가 스파이크에서 실패했을 때의 대안으로 둔다.

### Option C. 하이브리드: Evoke 셸 + `monaco-vscode-api`

`monaco-vscode-api`(CodinGame, MIT)는 VS Code 소스에서 워크벤치 서비스를 떼어 Monaco에 꽂을 수 있는 npm 패키지들로 낸다. 2026-11-10 기준 v39.0.4, VS Code 1.145 대응, 전날까지 커밋이 있다 [문서].

- **얻는 것**: ② 전체(서비스 단위로 골라 넣음), ③ 워커 확장 호스트 [문서], VSIX 로딩 [문서], VS Code 기본 확장(언어 문법 등)의 패키지 [문서], 디버그 서비스 [문서]. Node 확장은 VS Code 서버에 원격으로 붙는 방식을 문서가 안내한다 [문서].
- **UI**: 서비스만 쓰고 UI는 Evoke가 그릴 수 있다. VS Code의 뷰(탐색기, 검색, SCM, 디버그, 확장 트리 뷰, 웹뷰)를 Evoke가 정한 DOM 컨테이너에 붙이는 방식을 지원한다고 알고 있으나, 이번에 문서에서 확인하지 못했다 [미검증].
- **Evoke 코드 재사용**: 높다. 메인 프로세스, IPC, 터미널, 채팅, IDE 링크, 레이아웃 편집, 테마, 문자열이 남는다. 바뀌는 것은 에디터를 만드는 부분과 `ideTools`가 값을 얻는 곳이다.
- **비용과 위험**:
  - 메이저 버전이 39다. VS Code 월간 릴리스를 따라 자주 깨지는 변경이 온다. 버전을 고정하고 분기에 한 번 올리는 식으로 관리해야 한다.
  - 사실상 한 회사의 프로젝트다. 멈추면 Evoke가 그 포크를 떠안거나 Option B로 가야 한다.
  - Node 확장 호스트에 필요한 VS Code 서버를 어디서 구하는가. Microsoft가 배포하는 서버 바이너리는 Microsoft 라이선스다. Code - OSS에서 직접 빌드하거나 VSCodium의 빌드를 써야 한다 [미검증].
  - VS Code 코드는 한 페이지에서 한 번만 초기화되고 내릴 수 없다 [문서]. 프로젝트 전환을 지금처럼 가볍게 할 수 없을 수 있다.
  - 번들이 커진다. 지금 Monaco 0.52를 `@monaco-editor/react`로 쓰는데, 둘 다 교체 대상이다.
- **판정**: 재사용이 가장 많고 독자 UI와 양립한다. 단, 핵심 가정 세 개가 [미검증]이다. 스파이크 없이는 확정할 수 없다.

## 7. Evoke UI/UX 설계 원칙

기존 `DESIGN.md`가 이미 대부분을 정했다. 유지할 것과 빠진 것을 나눈다.

**유지 (DESIGN.md의 규칙)**

- 기능은 코드 편집기를 따르고, 모양은 따르지 않는다.
- 선택은 색이 아니라 모양으로 보인다. 모서리 반경은 0이다.
- 테마 블록 밖에서는 변수만 쓴다. REBEL의 빨강은 하나다.
- 모션은 80~260ms, 진입과 선택에만. 입력을 늦추지 않는다. 모션 줄이기 설정을 지킨다.
- 다른 제품의 로고, 캐릭터, 화면을 복제하지 않는다. Cursor를 참조하지 않는다.

**빠진 것**

| 요소 | 현재 [확인] | 필요한 것 |
|---|---|---|
| Color Tokens | 역할 토큰 약 17개 (`style.css:5-20`). 그런데 `[data-theme='rebel']` 블록 안팎에 `#FFFFFF`, `#000000`이 직접 박혀 있다 (`style.css:25-40`). | 상태 토큰(오류, 경고, 성공, 정보)과 diff 색(추가, 삭제)을 더한다. VS Code 뷰를 붙이려면 Evoke 토큰 → VS Code 색 키의 대응표가 필요하다. |
| Typography | 글꼴 3종, 크기는 CSS 곳곳에 숫자로 | 크기 단계 토큰 |
| Spacing / Radius / Borders | 토큰 없음. 반경은 규칙상 0. | 간격 단계 토큰. 반경은 테마가 정할 수 있는 토큰으로 둔다(새 테마를 위해). |
| Elevation | "단단한 그림자, 어긋난 판" 규칙만 | 층 단계 토큰 (판, 시트, 떠 있는 위젯, 알림) |
| Icon System | 파일 종류 글자 배지(`FileIcon`), 유니코드 기호(◧ ◨ ⚙ ▸) | 아이콘 집합 하나. 확장이 주는 아이콘(codicon, 파일 아이콘 테마)을 어떻게 다룰지 정해야 한다. |
| Component States | DESIGN.md에 표가 있음 | 유지 |
| Motion | 있음 | 지속 시간과 곡선을 토큰으로 |
| Panel / Navigation / Tabs | CSS 클래스로만 존재 | React 컴포넌트로 뽑는다 (`Panel`, `TabStrip`, `Row`, `Sheet`). 지금은 `App.tsx` 안에 마크업이 반복된다. |
| Command Interface | 없음 | 명령 팔레트. 빠른 열기 시트(`App.tsx:766-797`)를 그대로 넓힌다. |

**테마는 색 이상이다.** 지금도 REBEL은 색만 바꾸지 않는다. 글자 조각 칩, 잘린 모서리, 배경 그림, 선택 모양이 다르다. 다만 그 방식이 `[data-theme='rebel'] .클래스` 재정의 수십 줄이다. 세 번째 테마를 넣으려면 CSS 파일 전체를 알아야 한다.

제안: 테마 하나를 **토큰 + 모양 변수 + 선택적 CSS 조각**으로 정의한다. 모양 변수는 지금 선택자로 갈리는 것들이다 (칩 모양, 선택 모양, 기울기 각도, 그림자 어긋남). 컴포넌트는 변수만 읽는다. 변수로 표현 못 하는 것(REBEL의 글자별 칩)만 테마의 CSS 조각에 남긴다.

**테마와 레이아웃의 분리**: 지금 한 군데가 엮여 있다. 작업 영역 크기 측정이 `theme`에 의존한다 (`App.tsx:459`, 테마마다 상단 바 높이가 달라서). 저장되는 좌표가 분수라서 결과는 안전하지만, 패널 최소 크기(`LIMITS`, `layout.ts:21`)는 픽셀이고 TIDE의 메뉴 그림 높이를 근거로 한다. 새 테마가 이 최소값을 바꾸고 싶어질 것이다. 규칙: **테마는 `LIMITS`를 바꾸지 못한다.** 테마가 못 맞추면 테마 쪽 그림을 줄인다.

### 8.3 제안: 사각형 모델을 유지하고 두 가지만 넓힌다

도킹 트리(분할 노드와 탭 스택으로 된 트리)로 갈아타지 않는다. 지금의 사각형 모델이 도킹 위치를 이미 표현하고, 테스트된 기하 코드를 버리게 되기 때문이다.

```ts
// 지금
type Layout = { main: Record<MainId, Rect> | null; floats: Partial<Record<FloatId, Rect>> }

// 제안 (version: 2)
type PanelId = string                       // 레지스트리에 등록된 id
type Layout = {
  version: 2
  panels: Record<PanelId, { rect: Rect; tools: ToolId[]; active: ToolId; hidden?: boolean }> | null
  floats: Partial<Record<FloatId, Rect>>
}
```

1. **패널을 레지스트리로.** `MAIN_IDS`와 `LIMITS`를 고정 유니언에서 등록된 목록으로 바꾼다. `moveRect`, `resizeRect`, `fillHidden`은 이미 id 배열을 돌기 때문에 시그니처가 거의 그대로다.
2. **패널은 도구의 순서 있는 목록을 갖는다.** 도구는 미리 정해진 컴포넌트다: 파일, 변경, 검색, 에디터 그룹, Claude 터미널, 채팅, Codex, 셸, 에이전트 센터, 문제, 디버그 등. 사용자는 도구를 만들지 못하고, 옮기고 숨기고 순서를 바꿀 뿐이다(요구 사항의 "컴포넌트 중심" 제한).
   - 분할 = 패널의 사각형을 반으로 나눠 새 패널을 만들고 도구 하나를 옮긴다.
   - 에디터 분할 = 에디터 그룹 도구가 두 패널에 있는 것.
   - 도구를 다른 패널에 놓기 = 편집 모드에서 도구 칩을 끌어 놓는다. 기존 `pointed`(`LayoutEdit.tsx:68`)의 "어느 패널 위인가" 판정을 그대로 쓴다.
3. **기본 프리셋**을 코드에 둔다: 기본, 에이전트 중심(에디터를 줄이고 에이전트 패널 둘), 편집 중심, 리뷰(diff와 변경 목록 나란히).
4. **v1 → v2 변환**은 `parseLayout`이 한다. v1의 `pane/center/right` 사각형을 그대로 세 패널로 옮기고 도구 목록은 기본값을 채운다. `split`의 폭과 접힘도 같이 옮긴다.

**사이드바 메뉴 순서**에는 제약이 있다. TIDE의 메뉴 이름은 그림(`plugins/evoke/scenes/*.png`) 위의 정해진 줄에 놓인다 (`ITEM_ROWS`, `tokens.js`). 데스크톱 쪽 순서를 바꾸게 하려면 데스크톱의 메뉴를 그림이 아니라 글자로 그려야 한다. 데스크톱 `Pane.tsx`가 그림에 얼마나 묶여 있는지는 Phase 4에서 확인한다 [미검증].

## 9. AI Workspace 구조

### 9.1 지금의 연동 방식 [확인]

**Claude Code: 세 가지 통로**

1. **PTY** (`main.cjs:242-273`). 로그인 셸에서 `claude` 또는 `claude --resume <uuid>`. 환경 변수 `CLAUDE_CODE_SSE_PORT`, `ENABLE_IDE_INTEGRATION`을 넣어 IDE 링크를 찾게 한다. `TERM_PROGRAM`은 지운다(xterm.js가 이미지를 못 그려서 플러그인이 일반 줄로 떨어지게).
2. **IDE 링크** (`ide.cjs`). `127.0.0.1`의 임의 포트 WebSocket. 락 파일의 토큰을 `x-claude-code-ide-authorization` 헤더로 받아 상수 시간 비교한다. MCP 메서드 `initialize`, `tools/list`, `tools/call`. 도구 호출은 메인 → 창(`ide:call`) → `ideTools` → 응답(`ide:reply`)으로 돈다. `openDiff`는 사용자가 수락/거절할 때까지 응답을 미루는 Promise다 (`App.tsx:244-252`).
3. **stream-json 프로세스** (`main.cjs:276-310`). 프로젝트당 하나. 줄 단위 JSON 이벤트. 권한 요청(`control_request`/`can_use_tool`)에 `control_response`로 답한다.

**Codex: 통로 하나.** PTY에서 `codex`. 프로젝트 목록은 `~/.codex/config.toml`의 신뢰 폴더에서 읽는다 (`codexTrusted`).

**세션 식별**: `${kind}:${cwd}` (`App.tsx:908`), 채팅은 `chat:${cwd}` (`ChatPanel.tsx:9`). **같은 프로젝트에서 같은 종류의 에이전트를 두 개 돌릴 수 없다.** 병렬 작업의 첫 번째 장벽이다.

**상태**: 채팅은 `busy` 플래그가 있다. PTY 세션은 "살아 있음/종료 코드"만 안다. 에이전트가 일하는 중인지, 입력을 기다리는지, 권한을 묻는 중인지 모른다.

## 부록 A. 가장 먼저 개발해야 하는 작업 5개

1. **엔진 스파이크** (Phase 0). 버릴 브랜치에서 `monaco-vscode-api` + 별도 프로세스 확장 호스트로 Open VSX의 Node 확장 하나를 돌린다. 이 결과가 아키텍처를 정한다.
2. **설정 저장을 메인 프로세스 파일로 이전** (`settings.json`, `layout.json`, `theme.json`, `workspaces/*.json`) + `localStorage` 마이그레이션. 이후의 모든 변경이 이것을 전제로 한다.
3. **`App.tsx` 분해와 엔진 인터페이스**. `ideTools`가 이미 쓰는 다섯 동작(`openFile`, `openDiff`, 선택, 진단, 저장)을 경계로 삼는다. 명령 레지스트리를 같이 만든다.
4. **에이전트 세션 레지스트리**. `${kind}:${cwd}` id를 고유 id로 바꾸고 `terms`와 `chats`를 합친다. 병렬 작업과 Agent Center의 전제다.
5. **레이아웃 v2**. `MainId` 고정 유니언을 패널 레지스트리로, 패널에 도구 목록을. `layout.ts`의 기하 함수와 테스트는 그대로 쓴다.

## 부록 B. 기존 코드에서 반드시 보존해야 하는 기능

- **파일 접근 가드**: realpath 검사, 신뢰된 폴더만 열기 (`main.cjs:21-51`).
- **렌더러 격리**: `sandbox`, `contextIsolation`, 탐색/새 창 금지, CSP, Electron fuse.
- **Claude Code IDE 링크**: 락 파일, 토큰 검사, 도구 11개, `openDiff` 수락/거절, 선택 영역 알림 (`ide.cjs`, `App.tsx:221-291`).

- **`⌘L` 선택 영역 전달**, 저장 시 포맷, 미리보기 탭, 창에 돌아오면 디스크 내용 반영.
- **미리보기 서버**: 토큰 경로, 루프백, 자기 주소만 외부 브라우저로.
- **UI 편집 모드 전체**: 이동, 크기, 스냅, 가이드, 교환, 숫자 입력, 프리셋, 미리보기, 초안/저장 (`layout.ts`, `LayoutEdit.tsx`).

- **TIDE와 REBEL**, Dock/작업 표시줄 아이콘이 테마를 따르는 것, 모션 줄이기.

## 부록 C. 가장 큰 기술적 위험 5개

1. Node 확장 호스트가 Evoke의 프로세스 구조에서 동작하는지 검증되지 않았다. (11절 1번)
2. `monaco-vscode-api` 하나에 호환성 전체가 걸린다. (2번)
3. 확장이 지금의 보안 경계를 무력화한다. (3번)
4. Marketplace와 Microsoft 전용 확장은 라이선스로 막혀 있고 기술로 풀 수 없다. (4번)
5. 테스트 없는 1,045줄 `App.tsx`를 분해하면서 생기는 회귀, 그리고 로딩 주소 변경으로 인한 설정 유실. (6, 7번)

## 부록 D. 아키텍처 전환 여부와 그 이유

**Code - OSS로 전환하지 않는다. 편집 엔진만 교체한다 (Option C, 스파이크 조건부).**

- Evoke의 정체성은 워크벤치 밖에 있다. 자유 배치 편집 모드, 두 테마의 모양, 에이전트 터미널과 IDE 링크. Code - OSS로 가면 이것들을 워크벤치의 규칙 안에서 다시 만들어야 하고, 고친 만큼 매달 업스트림 병합 비용을 낸다.
- 지금 코드에서 한계에 닿은 곳은 편집 엔진 한 곳이다. 메인 프로세스, IPC, 터미널, 에이전트 연동, 레이아웃, 테마는 구조를 유지한 채 넓힐 수 있다(3절).
- 맨 Monaco를 유지하는 길(Option A)은 확장 실행을 포기하는 길이다. 제품 정의와 맞지 않는다.
- Option C의 핵심 가정은 아직 검증되지 않았다. 그래서 첫 작업이 스파이크이고, 실패 시 전환 대상(Theia 우선, 다음이 Code - OSS 포크)과 그때 살아남을 경계(엔진 인터페이스)를 미리 정해 두었다.
- 어느 길로 가든 달라지지 않는 사실: Marketplace는 못 쓰고 Open VSX를 쓴다. Microsoft 전용 확장은 못 쓴다. "VS Code에서 쓰던 것을 그대로"는 그 범위 안에서만 성립한다.
